# ADR-0008: Flight date readiness and deterministic Aviasales handoff

- Status: accepted for MVP
- Date: 2026-07-15

## Context

Карточка направления переводит пользователя из выбора места в поиск авиабилетов. Для такого
перехода одного месяца недостаточно: Aviasales принимает конкретные `depart_date` и `return_date`,
а молча выбранные приложением даты создают ложную точность и ухудшают качество перехода.

При этом собственный перебор тарифов по матрице «дата вылета × длительность» требует flight API,
ценовых данных, rate-limit policy и отдельной оценки вариантов. Это другой продуктовый slice и не
должно скрытно появляться внутри простой navigation-ссылки.

## Decision

### Temporal readiness

Период поездки является P0-определённым, если выполнен один из контрактов:

1. известны обе точные даты `date_from` и `date_to`;
2. известна опорная дата или месяц вылета и хотя бы `duration_nights_min`.

Если известен месяц или одна дата, но длительность неизвестна, pipeline задаёт P0-вопрос о
примерном количестве ночей. `duration_nights_max` уточняет диапазон, но не является обязательным.
Точные даты имеют приоритет и не требуют отдельного вопроса о длительности.

### Deterministic date options

Backend возвращает typed варианты дат для commerce handoff:

- при точных датах — один вариант с источником `exact`;
- при одной дате вылета и длительности — до трёх вариантов возврата по подтверждённому диапазону
  ночей;
- при месяце и длительности — до трёх явно помеченных `derived`-вариантов внутри ближайшего
  будущего вхождения этого месяца.

Для derived-вариантов используются только подтверждённый месяц и диапазон длительности. Дата
возврата всегда вычисляется как `departure_date + duration_nights`; цены, наличие и «самый дешёвый
день» не предполагаются. Все даты должны быть не раньше текущей даты и не дальше одного года.

Диапазон длительности сводится к уникальному набору `min`, округлённая середина и `max`. Для месяца
им соответствуют ранний, средний и поздний допустимый старт; каждый возврат остаётся внутри
выбранного месяца. Если конкретная длительность не помещается в оставшуюся часть месяца, такой
вариант не показывается. При одной точной дате вылета те же длительности дают разные даты возврата.

### Card interaction

При одном точном варианте CTA сразу показывает диапазон и открывает Aviasales. При derived-вариантах
CTA раскрывает компактный выбор конкретных дат в карточке. Только клик по конкретному диапазону
открывает внешний поиск.

Deep-link передаёт origin/destination IATA, пассажиров, `depart_date` и `return_date` в формате
`YYYY-MM-DD`. Выбор navigation-пресета сам по себе не изменяет основной `TravelRequest`: глобальное
изменение критериев по-прежнему требует явного сообщения или подтверждённого refinement.

Событие `travel_link_opened` хранит только режим дат `exact | derived`, но не сами даты. Это
позволяет сравнивать CTR без расширения объёма пользовательских данных в аналитике.

## Consequences

- Month-only запрос больше не считается достаточным для завершения подборки без длительности.
- В Aviasales не уходит квалифицированный переход без конкретной пары дат.
- Пользователь видит, какие даты были подтверждены, а какие предложены интерфейсом.
- Детерминированная генерация вариантов покрывается unit tests и не зависит от LLM.
- Для старых локальных snapshot без typed date options UI безопасно просит обновить условия поездки.

## Deferred work

Поиск лучших цен по гибким датам требует отдельного flight-provider adapter. Такой slice сможет
перебирать departure window и duration range, учитывать реальные тарифы и возвращать evidence с
ценой и freshness. До этого derived-варианты являются только навигационными пресетами.

## Rejected alternatives

- Открывать month-only ссылку как готовый поиск: пользователь повторно вводит главный параметр.
- Молча выбирать середину месяца: неподтверждённая дата выглядит фактом.
- Перебирать цены через browser/deep-links: результат нельзя надёжно нормализовать или доказать.
- Считать клик по пресету изменением всей поездки: скрытая мутация ломает модель chat memory.
