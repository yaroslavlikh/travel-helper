# Как считается стоимость поездки

Статус: действующий первый pricing-срез (modelled catalog). Код:
`app/pricing/estimator.py`; публичный контракт: `app/pricing/models.py`.

## Короткий ответ

Нет, LLM не считает цену и не назначает бюджетный статус. Все числа, суммы, сравнения с бюджетом
и порядок карточек вычисляются обычным детерминированным Python-кодом. LLM может только извлечь
из сообщения пользователя явные условия — например, даты, число путешественников и бюджет — и
сформулировать текстовое объяснение уже посчитанного результата.

## Что означает цена в карточке

Это ориентир на **всю поездку для всей указанной группы**, а не цена одного билета или одного
человека. Для каждого направления сервис строит три суммы:

| Значение | Смысл | Как показывается |
| --- | --- | --- |
| `floor` | достижимый минимум при экономии | «от … при экономии» |
| `expected` | реалистичный плановый ориентир | начало главного диапазона |
| `safe` | бюджет с небольшим запасом на неопределённость | конец главного диапазона |

Главная цифра — `expected–safe`. Нижняя граница не показывается как равноправный прогноз: это
возможный экономный сценарий, а не ожидаемая цена.

## Текущий алгоритм

Пока нет подключённых live/cached провайдеров, входными данными служат явно помеченные локальные
baseline-значения demo-каталога. Поэтому карточка помечена `ESTIMATE` и не утверждает наличие или
актуальную цену.

1. Берутся отдельные baseline-компоненты кандидата: перелёт, жильё и расходы на месте.
2. Перелёт и расходы на месте умножаются на вес группы: взрослый — `1.0`, ребёнок — `0.6`,
   младенец — `0.2`.
3. Жильё считается по числу комнат: 1–2 взрослых — одна комната, далее `ceil(adults / 2)`.
4. Для каждого компонента строится диапазон `low / expected / high`; `expected` — середина
   модельного диапазона.
5. Итоговые суммы:

```text
floor    = сумма low: перелёт + жильё + расходы + обязательные сборы
expected = сумма expected тех же компонентов
safe     = сумма high + небольшой запас
запас    = max(3 000 ₽, 5% × expected расходов на месте)
```

Обязательные сборы сейчас не имеют отдельного источника в fixture и не превращаются в выдуманное
число. Это явно видно в assumptions/warnings, а не маскируется нулём как подтверждённый факт.

## Даты, состав группы и ограничения

- При точных датах число ночей — разница между датой вылета и возвращения.
- Для месяца, окна вылета или неизвестного периода применяется сохранённая длительность, иначе
  default 7 ночей; карточка показывает, что это допущение.
- Багаж не получает нулевую доплату: в текущем modelled-срезе его цена не подтверждена и выводится
  как assumption.
- Неподдерживаемые live-факты — наличие, сборы отеля, визы и курс — не выдаются за рассчитанные.

## Как определяется попадание в бюджет

| Статус | Условие |
| --- | --- |
| Вписывается с запасом | `safe <= budget` |
| Вписывается, но запас небольшой | `expected <= budget < safe` |
| Только при экономии | `floor <= budget < expected` |
| Выше бюджета | `floor > budget` |
| Недостаточно данных | бюджет или критичный компонент отсутствуют |

Для `budget_strict=true` hard filter проходит **только** первый случай: безопасная сумма должна
укладываться в лимит. Если после прочих hard filters остаются лишь дорогие варианты, интерфейс
может показать их как fallback, но они остаются `passed_hard_filters=false` и содержат явное
предупреждение.

## Снапшоты и субчат

На каждый результат создаются `pricing_snapshot_id` и `recommendation_snapshot_id`. Субчат
обсуждает сохранённую карточку, включая её breakdown и assumptions, а не запускает новый ranking
в момент вопроса. Уточнение в основном чате формирует новый snapshot; само обсуждение карточки
не меняет общую подборку.

## Что будет добавлено позже

Live и cached flight/hotel providers смогут подменить входные компоненты, но не формулу и не API
карточки. Тогда для каждого компонента появятся provider, тип источника, время наблюдения, TTL и
confidence. До этого `ESTIMATE` — честный planning baseline, а внешние Aviasales/Яндекс-ссылки
остаются переходами, а не доказательством цены.
